# 增量研究与续做

## 成果所有权

默认研究目录为目标仓库内 `research/code-agent/`。已有成果先检查结构与范围，尽量适配，未经必要判断不整套重写。

- index 是导航、范围、有效基线和研究状态的唯一汇总入口。
- 专题保存机制细节，证据台账保存可复用证据；Overview 和系统结论引用它们，避免多处复制同一细节。
- progress 保存当前批次、未解问题与下一步，不能仅写“继续分析”。

状态建议：未研究、概览、深入中、已收束（可含未知）、待复核。深度与状态分开记录：“已收束”不自动表示运行验证完成。不要为满足状态标签掩盖缺口。

## 基线与增量

1. 读取 index、progress、相关专题和证据；确认用户当前意图与已确认范围。
2. 比较旧基线和当前 commit、本地改动。记录未提交变化的相关摘要或安全的内容指纹。没有 Git 时记录可获得的文件版本/指纹，并说明限制。
3. 从变更路径和符号追踪调用方、消费者、协议和状态契约，判断影响范围；不能只因专题文件未改就认定结论仍有效。
4. 为每个受影响结论指定复核动作；基线丢失或差异过大时承认无法局部证明，重新核验相关主链路。
5. 修改专题后同步修正 Overview、系统结论和 index。未复核文档保留原基线并标记，不把整套成果统一盖上新 commit。
6. 重要更正记录旧结论、新结论、原因、证据和影响文档。保留简短记录即可，不生成彼此竞争的多份“最新版”。

读者对某机制提出“仍无法据报告实现”的反馈时，不能只给该段补一句解释：先追准判定与状态动作，再扫描同批相邻专题的同类笼统表述；修订真实受影响处，在 progress 保存读者粒度偏好并回写 Skill 验收，防止跨设备继续时退回浅层目录/函数罗列。记录哪些专题已复核、哪些仍待复核，不能用一个“已全部深入”状态覆盖不同成熟度。

## 中断与上下文恢复

每完成一个机制、形成重要结论、出现阻碍或准备压缩上下文时落盘。progress 至少保留：

- 当前目标、本批范围、用户已确认的取舍。
- 已读的关键文件/符号及对应证据 ID，不堆砌全部搜索结果。
- 已确定结论与仍在竞争的解释。
- 运行过的命令、结果、环境限制和仍在运行的进程。
- 下一步具体动作及完成它能回答的问题。
- 未完成文档及隔离验证产物位置。

恢复时先检查基线变化，再继续。不要把旧 Agent 的摘要当源码证据；关键主张应能回到台账定位。

## 并行研究（可选）

只有环境允许并且存在可独立研究的专题时才使用子 Agent，不创建用户可见的新任务作为替代。给每个研究者同一基线、明确范围、证据标准和产物位置。避免同时修改 index 与 Overview；主研究者负责合并冲突、跨模块核对和最终更新。没有子 Agent 时顺序执行同一流程。
