# 中文报告与索引模板

这些是内容骨架，不是固定篇幅或图数量要求。根据真实仓库合并或调整章节，保留总分总阅读路径。代码符号保留原名，正文中文；基础 Agent 知识不重复铺陈，难点用具体实例。

## index.md

开头给出研究目标、仓库位置、当前批次、基线与整体覆盖声明。

| 文档/机制 | 深度 | 状态 | 有效基线 | 关键未知或缺口 | 关联文档 |
| --------- | ---- | ---- | -------- | -------------- | -------- |

链接到 Overview、专题、系统结论、证据和进度。注明下一阅读路径和待研究优先级。不要把“已概览”显示为“已深入”。

## overview.md

1. 系统解决什么问题，研究范围及已确认的主要结论。
2. 进程/组件边界与状态所有者：谁调度、谁持久化、谁构造请求、谁展示结果。
3. 一次任务的端到端过程：入口、指令与历史、模型、工具、反馈、继续/终止。
4. 关键数据表示及转换：持久化、运行时、Provider、UI。
5. 模块关联、重要变体、当前疑点和专题入口。

初版标为初步全景，收束时依据专题证据修正。无需把所有细节复制到 Overview。

## topics/<topic>.md

1. 本专题回答的问题、系统位置、基线和覆盖边界。
2. 整体流程与关键结论，必要时配序列图或状态图。
3. 按子步骤展开：触发 → 输入 → 实现 → 状态变化 → 输出/消费者。每步引用证据。
4. 贯穿示例：最小但能暴露难点的数据、时序或请求变化。假设输入明确标注；示例推演不是运行验证。
5. 关键异常、取消、重试、恢复和并发契约。
6. 原方案的取舍与适用边界，作者理由和分析推断分别标注。
7. 测试与运行验证、未知项及其结论影响。
8. 与其他专题的关联及应修正的全局结论。

涉及内容缩减或外置存储时增加一张逐层可恢复性表：处理层、输入、输出、完整副本、读取入口、生命周期、失败降级。涉及模型驱动的管理策略时注明哪些规则由代码强制，哪些只存在于提示词。

针对压缩专题，可按“触发与选取 → 摘要生成 → 历史替换 → 持久化 → 请求重建 → 续跑”展开，但以实际实现为准，不虚构不存在的阶段。

对于上下文、压缩、工具结果等一条输入会经过多个资源保护层的专题，开头先给**有明确阅读方向、连续步骤编号的主流程**，再以相同步骤编号列出分支的可执行判断标准、动作和下一站（包括失败和回环）。主图只承载主线；复杂条件放在邻接表或小图中，避免把所有箭头挤进一张难读的大图。阈值须注明单位、默认值、配置覆盖、估算与 Provider 权威值的区别；不存在的自动召回或统一裁剪步骤不得因流程示意而补造。

声称覆盖“整体上下文”时，主图至少让读者发现源码存在的正常完成、工具/续写回环、请求前保护与 Provider 超窗后的 Reactive 恢复；手动命令等独立入口在紧邻主图处标出，不必挤进同一张图。每条关键异常分支要有本专题的可读步骤或明确指向同等粒度的专题；不能靠全文搜索才发现它。若只完成局部研究，在标题、index 和试用记录中显式降低覆盖状态。

用户指定的复杂子模块还应在**同一专题文件**给自己的短流程图，并用相同步骤编号解释关键决策。**图本身**用白话呈现触发条件、扫描方向、候选筛选、分组/保留、对选中对象的准确动作以及提交/撤销条件，保留能帮助决策的关键数字；不要堆字母变量、源码字段或嵌套公式；不能把核心算法全留在图下，使图只剩“估算 → 裁剪”。紧接图下用中文名称和数字例子说明门槛怎么算，再给精确公式、配置名及默认值，随后解释输入/输出、持久边界和失败后果。阅读图不应要求读者先翻译代码变量。用一组最小消息序列或数字完整走通；图、表、例子共同解释核心分支，删掉重复叙述。图只画真实实现中的模块和条件，不因模板要求凭空增加节点。

研究上下文连续性时，必须逐项回答冷恢复何时发生、与 Provider cache 及压缩后重建有何区别；摘要请求实际收到哪些消息和哪份 Prompt；压缩前后分别为何估算 token；持久 transcript、最近原文、独立存储状态、诊断日志、外置文件、Skills/插件/Hook/记忆/Todo 各自如何继续可见。对每项写明“原始事实是否保留、模型是否自动再次看到、需要什么读取/重注入动作”，不要用“上下文恢复”笼统代替。区分当前 Session 冷恢复、跨 Session 按需读取、跨会话项目/子代理记忆；有名为 SessionMemory 的枚举时仍须追生产触发点，不能根据命名补造流程。

解释压缩后内容时，至少选一个贴近真实任务的**假设性消息序列**，逐项展示“压缩前来源 → 是否参与通用摘要 → 压缩后具体提示文字/结构 → 下一次请求是否自动可见 → 冷恢复依据”。对 Plan/Skill/Memory/Plugin 等易混淆对象，查实际 Prompt 或格式化函数；明确 Skill 目录、Skill 正文、Skill 调用后的操作轨迹是否由不同机制保留。若没有专属执行轨迹摘要器，指出仅可能由通用摘要模型概括，不把 prompt 要求误写为保证。

## synthesis.md

回到系统解释整体设计：哪些机制相互依赖，局部选择形成了哪些系统性质和限制。迁移建议说明“原问题 → 原机制 → 收益/代价 → 采用条件 → 必须保持的契约 → 尚需验证”。不把项目特定限制变成通用最佳实践，也不默认分析用户自己的代码。

## research/evidence.md

以可链接的证据 ID 记录：主张、类型、基线、源码符号与定位、适用条件、测试或命令结果、限制、被哪些文档引用。多个主张可共享原始证据，但不能用同一个宽泛引用支持无关结论。

日志仅保存必要片段并脱敏，避免将巨大原始输出灌入正文。大台账可按专题拆分并维护导航。

## research/progress.md

当前批次与确认范围、阶段完成情况、未解问题、下一步具体操作、重要更正记录、验证产物与环境限制。内容要求见 [增量与续做](continuity.md)。

## 图与代码片段

组件图用于边界和所有者，序列图用于事件顺序，状态图用于转换条件。箭头标明调用/事件/数据含义，不能只连模块名称。图与正文主张引用同一组证据。

使用 Mermaid 时，以目标阅读环境采用的 Mermaid 版本解析全部图块；Markdown 格式检查不能替代图语法检查。特别避免把 `loop`、`end` 等语法关键字用作参与者或节点 ID。无法运行解析器时明确记录未验证。

代码片段只保留解释关键分支或契约所需部分，链接到完整实现；伪代码注明省略和简化。不得用图多、代码长或引用密集替代解释。
