# 证据与深度标准

## 证据类型

| 类型     | 能支持的说法                             | 必须记录                                    |
| -------- | ---------------------------------------- | ------------------------------------------- |
| 源码确认 | 某基线下存在具体控制流、字段、转换或契约 | 文件、符号、行号或稳定定位、基线、适用条件  |
| 测试支持 | 测试声明并覆盖了某场景                   | 测试定位、输入、断言；未执行则明确标注      |
| 运行验证 | 本次实际命令在指定条件下产生结果         | 命令、cwd、环境摘要、退出码、关键输出、限制 |
| 推断     | 多项证据支持一种解释，但未直接证明       | 前提、支撑证据、替代解释与置信边界          |
| 未知     | 尚不足以作出结论                         | 搜索/验证范围、阻碍、影响、下一步           |

一个结论可以同时有几类证据。测试通过只支持其覆盖的条件；运行某个 mock 测试不能证明真实 Provider 行为。文档与代码冲突时以当前执行路径说明行为，另记冲突；设计动机可引用文档、注释或历史讨论并注明时间。

证据引用靠近具体主张。采用目标仓库相对路径加符号、行号、commit，并尽可能提供可点击链接。工作区未提交代码需记录相关 diff 或内容摘要；避免记录秘密。版本变化后旧行号不可冒充新位置。

“未找到”只能说明查证范围。确认不支持某能力需要足够的边界证据，例如完整注册入口、能力枚举、明确拒绝分支和相关适配路径；否则写未知或当前路径未发现。

## 深度判定

概览解释组件职责、所有者、输入输出和主链路位置。重点机制必须解释：

1. 谁在什么条件下触发，入口如何到达关键实现。
2. 输入的形状、来源和约束，输出由谁消费。
3. 状态由谁读写，何时提交，何时可见，如何关联身份。
4. 关键分支、失败、重试、取消和恢复如何改变行为；不适用的分支说明原因。
5. 对上游/下游的契约，包括顺序、幂等、并发、部分完成和迟到结果。
6. 测试和运行证据支持到何处，哪些结论仍有边界。
7. 方案收益与代价，迁移所需条件；替代方案是研究者建议时明确标注。

若同一机制经过多层预算、截断、压缩或持久化，逐层记录“进入内容、离开内容、完整副本位置、可恢复入口”。后层保存预览不能证明原始内容可恢复。由提示词维持的行为约束与代码强制的 invariant 分别陈述。

对上下文清理，至少区分持久对话、运行时历史、本轮请求、诊断日志和 UI 投影。分别追写入与冷恢复读取路径；事件已产生不意味着持久 Session 会回放它，JSONL 中曾有请求原文也不意味着它是权威 transcript 或永久可读。

用户指定专题进一步拆解子步骤。以消息压缩为例：整体流程后分别讲预算检测、摘要输入和生成、历史替换、持久化、请求重建及继续执行；每步链接到真实实现，不假设这些步骤一定独立存在。

遇到正确性相关未知先作合理查证，不用“外部依赖”提前止步；当必要契约已明确时，不必追读无关 SDK 内部。允许有边界的未知结束，不因未知而无限重试。

## 校准样例（纯假设，不是仓库事实）

偏浅：系统并发执行工具，等待全部结束后把结果传回模型，并发降低了延迟。

达到目标的表达：模型返回调用 A、B、C，假设运行完成顺序为 B、C、A。调度器通过调用 ID 关联结果，Provider 适配器按 A、B、C 构建下一轮输入，因此 UI 完成顺序可能不同于模型输入顺序。接下来需要分别证明“如何关联”“在哪里排序”“谁持久化”；不能仅凭 Promise.all 推断所有层都保持同一顺序。单个失败是否变成工具结果、取消后是否写入迟到结果，也属于该机制的契约。

转成验收规则：必须从生产者追到实际消费者；顺序区分执行、完成、持久化和模型输入；难点用最小实例说明；每个实仓结论都有对应证据。此样例中的顺序策略不可直接套到真实仓库。
