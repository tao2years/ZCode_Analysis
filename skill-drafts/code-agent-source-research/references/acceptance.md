# Skill 试用与验收

结构验证只能证明文件和元数据符合要求，不能证明研究行为有效。首次试用前由用户选定真实仓库和小范围机制，不擅自把当前工作区视为研究对象。

## 建议试跑输入

“使用本 Skill 研究指定仓库中的一个机制。先建立足够的整体运行模型，再深入该机制，维护研究目录与 index。范围以用户选择为准。”

候选机制：并发工具结果汇合、压缩后的消息重建、大输出落盘与后续读取。选择实现边界相对清楚、能追到实际消费者的一个；不存在相应机制时与用户调整范围，不编造。

首次试跑用真实源码，检查研究推理和报告质量，不要求启动目标程序。若用独立子 Agent，仅提供 Skill、真实任务和最小原始材料，不给预设答案或先前研究结论。写入用户同意的研究目录，遵守目标仓库指令。

## 检查可观察行为

| 验收项     | 检查方法                                         | 不合格示例                                |
| ---------- | ------------------------------------------------ | ----------------------------------------- |
| 全景先行   | 能从入口讲到专题及后续消费者                     | 只有目录与功能清单                        |
| 深入实现   | 抽取一个核心主张，复查调用方、实现、数据和消费者 | 找到函数后停止                            |
| 表示分离   | 用实际数据解释各层转换；无该层则说明不适用       | 把 UI 消息当成完整模型输入                |
| 正确性分支 | 检查影响该机制的失败/取消/恢复                   | 只讲正常路径却称完整                      |
| 入口可发现性 | 从 Overview/总流程图出发，不使用全文搜索，能找到每个影响结论的触发分支、回环、失败去向及专项解释 | Reactive 等关键机制只藏在表格一行或末尾一句，却将整体上下文标为已完成 |
| 证据可信   | 抽查源码定位、测试内容及所声称的验证记录         | 将静态推演写成运行通过                    |
| 示例有用   | 例子能解释实际顺序、字段或状态差异               | 编造结果或只有抽象重复                    |
| 系统结论   | Overview、专题、借鉴互相一致且有边界             | 无条件称为最佳实践                        |
| 增量续做   | 另一上下文能从 index/progress 知道下一步         | 仅写“未完成，继续分析”                    |
| 未知处理   | 查证范围、影响和后续方法明确                     | 未找到即不支持                            |
| 分层损失   | 对压缩、截断和落盘逐层核对完整内容是否仍可恢复   | 看到 artifact path 就宣称原始输出完整保存 |
| 约束强度   | 区分代码/存储约束与提示词约束                    | 把 prompt 中的去重要求写成确定性保证      |

任何重大事实失真、证据类型混淆或范围伪装都需要修订；未知项本身不自动导致验收失败。对缺失运行条件，只评估已做的部分。`quick_validate.py` 只验 Skill 文件结构；即使源码事实散见于多个文件，若读者无法从声称的“完整流程”顺着它们理解主要分支，研究试用也不通过。

## 增量行为检查

完成首个专题后，追加一个紧邻子问题，检查是否复用已有全景而不重新访谈，是否同步修正 index 和受影响结论。可以用隔离副本构造一个与专题有关的小变化验证待复核标记，但不得为此修改真实产品代码。没有执行此检查时注明未测，不以阅读规则代替验证。

## 结果记录与修订

记录真实任务、源码基线、执行条件、产物、各验收项结果和具体问题。只针对已观察失败修订，不积累无依据的兜底规则。必要时重跑受影响场景。

分别报告：内容已生成、文件已创建、结构检查结果、静态源码试跑范围、已有测试能支持的范围、是否安装。仅在实际运行时报告运行验证范围；没有目标仓库时输出可执行试用方案，并明确 Skill 尚未用真实源码试跑。
