# Code Agent 源码深度研究

面向熟悉 Agent 开发的读者，先理解真实运行行为和技术方案，再解释设计取舍与迁移条件。最终报告应便于读者进一步加工为团队讲解材料。不默认修改产品代码，也不自动研究用户自研项目或给出其改造方案。

## 入口与启动

- **系统研究**：建立全景、提出深挖范围，确认一次后自主研究。
- **专题深入**：核验并复用全景，深入用户指定内容；没有全景时先补足系统位置与关联主链路，不将专题请求扩大为全仓穷尽研究。
- “继续”“追加专题”属于上述入口的延续。不要重复创建 Skill 时的需求访谈；只问本次缺少且影响执行的信息。

读取仓库自身指令，确认仓库位置、源码基线与本地改动。默认在目标仓库的 `research/code-agent/` 保存研究；存在已有目录或用户指定位置时优先复用。先读现有 index 和进度，勿覆盖无关内容。

开始研究前读取 [证据与深度标准](references/evidence-and-depth.md) 和 [增量与续做](references/continuity.md)。开始写报告时读取 [报告模板](references/report-templates.md)。领域问题库只加载与当前阶段相关的文件。

## 研究流程

### 1. 建立基线与初步全景

记录 commit、分支、本地变更、入口意图和范围。识别真实启动入口、进程与组件边界、状态所有者、外部依赖，沿一次用户任务追踪到模型调用、工具反馈、继续或终止。目录结构只用于定位。

先读取 [主链路问题库](references/core-mechanisms.md) 的相关部分。形成初步 Overview，明确哪些已证实、哪些仍待核验。区分持久化记录、运行时对象、模型实际输入和 UI 展示。

系统入口在此提交运行模型、深挖建议、覆盖缺口与优先级，等待用户确认一次。用户已经明确给定本批范围或此前已确认时直接沿用。专题入口不重复整轮确认；仅在新的关键歧义改变范围时询问。

### 2. 按重点深入

优先级：用户指定内容 → 支撑它的上下游与正确性分支 → 本批其他核心机制 → 可选扩展。

每个重点机制按“整体流程 → 子步骤”组织；追踪触发条件、输入输出、关键实现、状态所有者和变化、调用方、消费者、异常分支、设计取舍。不能在找到相关函数后停止。

以“熟悉 Agent 开发的读者能否据此实现相同关键行为”自检。明确算法操作单位、阈值和参数、候选谓词、排序/分组、替换/保留、失败回滚、状态与持久边界；用最小消息序列或数字复算一个结果。每个复杂子模块在同一专题用短流程图展开，**图用白话讲触发条件、扫描方向、选取与准确动作**，保留关键数字；公式、变量和配置名放在紧邻图的说明中，再补持久化和恢复边界，删去重复散文。运行时清理还须追冷恢复后是否反弹及实际兜底是否保证成功。用户指出一处深度缺口时，答完后主动检查相邻专题的同类问题并修订，不等逐文件提示；长期偏好随进度和 Skill 一起保存。细则见 [证据与深度标准](references/evidence-and-depth.md) 和 [报告模板](references/report-templates.md)。

用具体输入贯穿难点；指定专题可包含字段、关键代码、协议片段、伪代码及状态转换，但不逐行解释无关实现。默认以源码、已有测试和文档研究设计思想，不运行目标 Agent 或 Provider；只有用户明确要求行为验证，或某个关键事实无法通过静态证据判定且运行结果会改变结论时，才考虑隔离运行。测试代码存在与实际执行通过分别记录。

当交付物声称覆盖某个系统的“整体流程”时，从其入口图逐一走通正常、工具回环、主动预算保护、Provider 拒绝后的响应式恢复和显式命令入口（仅限源码实际存在者）。重要机制只在末尾一段或其他文件可检索到，不等于读者能从整体入口发现它；在当前专题给出入口、失败去向和链接。按 [试用验收](references/acceptance.md) 检查这一点，未通过时下调专题和 Skill 试用状态。

涉及记忆、扩展、子 Agent、权限及运维机制时，按需读取 [关联机制问题库](references/supporting-mechanisms.md)。发现问题库之外的重要机制时依据实际系统纳入，不强套模块分类。

### 3. 跨模块核对与系统收束

使用适用的端到端场景检查各专题是否共同解释同一系统：正常任务、多工具调用与失败、取消、压缩续跑、重启恢复。只验证当前范围相关场景，不强制全仓跑齐。

用证据修正 Overview 和受影响专题，消解冲突后形成系统级结论。工程借鉴包含原方案解决的问题、实现约束、收益、代价和迁移条件。区分作者明示理由与研究者推断，不凭实现反推作者意图为事实。

维护 index 的基线、深度、状态、关联文档及缺口。以证据和行为解释是否充分衡量完成，不以篇幅、图或引用数量衡量。

## 执行与收束边界

质量优先，不设固定时长或费用预算。默认可阅读 Git 历史、源码、已有测试和一手设计资料；不把安装依赖、启动目标 Agent、调用真实 Provider 或故障注入列为研究完成条件。若用户要求或关键结论确需运行验证，再按仓库指令选择最小实验。遵守宿主和仓库权限，不改无关配置、锁文件或产品代码。Codex/Claude Code 的工具并非必需依赖；用等效读取、搜索、命令能力执行，缺失能力如实记录。

源码研究旨在理解技术方案、状态边界、设计取舍和可迁移思想。把未运行的结论标为源码确认或推断即可；不要把“未运行”自动列为分析未完成。实际外部调用需要已有可用配置、凭据和运行条件；不得虚构运行结果，也不输出秘密或真实用户数据。

新增发现直接影响本批结论时继续追踪；独立扩展记入 index，不无限追查依赖内部实现。允许以有边界的未知收束：记录查证、剩余不确定性、影响与下一步验证方法。不要把未知写成不存在或不支持。

中断、资源不足或验证受阻时保存证据和续做记录，明确已完成范围与缺口。完成报告可含已披露未知；未研究或未复核的部分不能包装成完成。

## Skill 自身验收

本 Skill 的生成、结构检查、安装和实际试跑是不同状态。需要验证或改进本 Skill 时读取 [试用验收](references/acceptance.md)，用用户选定的小范围真实任务检验行为。没有真实执行条件时只交付方案并注明“尚未实测”。
