图 1　请求前治理 / MICROCOMPACT

两种微压缩策略的核心差别：结果全文替换与分级部分裁剪

比较触发、候选选择、内容变换与状态提交；两侧百分比属于不同的阈值定义，不能直接相减。

ZCode
自研方案
触发
空闲 > 60 分钟，或估算量 E ≥ MM = min(完整 Auto 门槛 × 90%，该门槛 − 2,000 token)；清理开关需开启。
压力 ≥ 40%：Soft；≥ 60%：Hard每档每周期最多一次；首次达到 60% 可同一请求执行两档。
候选
从旧到新扫描合格工具结果按 assistant 工具调用分组；最近 5 组合格结果保留原文。
已完成 turn 的旧只读/搜索结果Soft 保护最近 12 个 user turns；Hard 保护最近 8 个。
内容变换
整条 content → 固定占位符不保留头尾片段、预览或摘要；工具调用 ID 与参数不变。
Soft：>4,000 字符留头尾各 1,500
Hard：>1,000 字符留头部 1,000提示说明省略字符数；不清空 tool result block。
提交
至少节省 256 token 才提交只改活跃 Runtime 历史；持久 Session tool part 不改。
原始 transcript 保留成功 compact 重置 Soft/Hard 标志，失败不重置。
机制结论ZCode 以整条替换回收空间；自研方案以两级保护窗口和头/尾保留量控制信息损失。

图 2　Provider 超窗后 / REACTIVE COMPACT

恢复路径的差别：直接摘要旧轮，或先分轮裁剪工具结果

两者都希望保留当前任务的连续性，但失败请求如何重建、何时调用摘要模型并不相同。

ZCode
自研方案
01 超窗
普通模型请求被 Provider 拒绝检查一次性恢复标志、快速回填保护与可摘要历史。
普通模型请求被 Provider 拒绝先进入历史工具结果的局部治理。
02 第一响应
当前失败请求 → 旧轮摘要按 assistant-started rounds 分组；最近至少一组保持原文。
超额量驱动工具裁剪，最多三轮每轮裁剪后重新请求 Provider，以反馈决定是否继续。
03 兜底
摘要请求可重选旧 / 新组边界若摘要自身超窗，缩小摘要输入；Reactive 不丢最旧组。
三轮仍超窗 → 压缩前一轮正常消息随后拼回本轮增量消息，构成新的当前请求。
04 续跑
提交摘要与边界，重试同一 model step再次超窗不无限重复本步骤的 Reactive 完整压缩。
用“旧摘要 + 本轮增量”继续任务把工具结果局部裁剪置于摘要之前。
关键界限ZCode 从当前失败请求分组摘要；它没有显式回退到上一轮成功请求后再拼接本轮增量。
