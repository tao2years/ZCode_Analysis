# 研究读者与深度约定

本文件记录用户在连续追问中确认的长期偏好，供跨设备或上下文压缩后继续研究使用。它约束**研究报告与 Skill 的写法**，不是目标 ZCode 源码自身的设计文档。

- 读者熟悉 Agent 开发；报告首先服务于理解别人的工程方案，之后可能被加工为团队讲解。目标是让读者能据报告实现同等关键行为，而不只是知道模块名称。
- 先交代一条输入的端到端主链路，再把复杂子模块在**同一专题文件**拆为编号小流程；图有清楚阅读方向、判断条件和失败去向。图、规则表和一个可复算例子共同承载核心机制，避免大横图和重复散文。
- 子流程图本身必须足以看出**何时触发、按什么顺序扫描、筛选谁、对谁做什么替换或保留、何时提交/撤销**；能写进节点的阈值公式、变量名和默认值不要藏到图下长段落。图下再说明参数来源、持久边界、冷恢复及反例。图不能只写“估算 → 裁剪 → 提交”。
- 研究每个重点机制时，主动追：触发公式与参数来源、输入表示、候选筛选、排序/分组、真正的操作单位、保留/替换算法、收益门槛、回滚条件、状态所有者与持久边界、下一消费者、异常与缓存代价。特别区分“每步检查”“触发后计算”“确实修改状态”。
- 例如“裁剪结果”必须写明是整条替换、保留 head/tail、截中间、落盘引用还是摘要；若实际按 UTF-8 bytes、JS 字符或本地估算 Token 计算，应分别标注，给数字使读者能复算。只写“清理旧结果”或“达到阈值压缩”视为深度不合格。
- 对多个表示保持区分：持久 Session、运行时历史、本轮 entries、Provider-neutral 投影、最终 wire 请求、UI 展示、诊断 JSONL、外置 artifact。任何“可恢复”都要说清从哪层恢复、需不需要显式读取。
- 运行时清理若不持久化，必须继续追**退出后恢复的反弹路径**：持久原文如何重建、下次模型步哪些策略会重新触发、估算基线是否仍代表重建后的输入、Provider 超窗后的恢复能否保证成功。不要只说“冷恢复会重建”就停下。
- 用户提出一个细节质疑时，先完整回答，再**主动扫描相邻专题**是否有同类深度缺口或相互矛盾，不等待用户逐文件提醒。发现应修订时在适当汇总点同步更新专题、证据台账、Overview/index 中受影响结论、Skill 验收和 handoff；不为了形式一次性重写无关专题。
- 学习思想与取舍为主，默认静态研究；未运行目标 Agent/Provider 时把可复算的源码推演标为假设例子，不冒充运行事实。外部 Provider 命中率、精确 tokenizer 等要标成未知，不因此省略源码内可证明的机制。
- 控制篇幅：优先保留能改变实现决策的公式、数据结构、分支、反例和迁移约束；删去重复的抽象概括。质量由可复现性与证据决定，而非页数、图数、引用数。

跨设备恢复先读 [进度](progress.md) 与本约定，再从 [索引](../index.md) 进入受影响专题。后续用户新反馈可直接修订此文件与 Skill，不重新访谈已经确认的偏好。
