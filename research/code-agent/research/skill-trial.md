## 本次发现的 Skill 改进点

1. 大输出必须按“执行捕获 → 工具格式化 → 通用序列化 → artifact → Provider 回灌”逐层核对。后层保存内容不能补回前层已丢弃的字节。
2. compact 不能只写成一种摘要操作；需要区分完整摘要压缩、microcompact 和 Provider 处理，并核对持久化与冷恢复语义。
3. Memory 的去重、冲突和过期策略需要区分代码强制与提示词约束，不能把模型应遵守的规则写成系统 invariant。
4. 试跑状态要分别报告静态源码、测试支持和真实运行，防止“已实测”掩盖验证层级。

以上四项已反写到问题库、证据深度标准、报告模板和试用验收规则。后续 E38 又证实原“表示分离：通过”的判断过早：报告虽列了四层表示，却把 Memory 的 durable 判定快照误当模型输入。因此该项现在也待复核，不能用表格结构代替真实数据流追踪。

## 用户后续校准（2026-09-22）

Microcompact 的第一版虽有触发阈值和白名单，但读者仍无法判断“整条替换还是留 preview、对哪些批次、如何计算收益”。用户要求报告达到可复现程度，并要求主动把同一粒度扩展到相关模块，不再逐段提醒。为此，B5 加入保持源码顺序的伪代码与数字例子；A1/A2/B1/B2/B3/B4 同批复核；Skill 核心流程和深度标准加入主动相邻审查。持久读者偏好见 [研究读者与深度约定](reader-contract.md)。这些修订已做结构与静态检查，**尚未由用户确认达到预期，也未运行目标 Agent/Provider**。

用户再次指出 Reactive compact 在“整体上下文功能”中不可见。回查发现它仅在 B5 的一行表格与末尾段落提及，未进入主流程图，也没有同页独立小流程。修订后应按**读者是否能从入口图找到机制、顺着触发到失败去向完成解释**复核，而不是按 `rg` 能否搜到关键词打勾。本试用记录先前将“正确性分支”标为通过，是验收判断错误；Skill 的结构校验和源码引用数量都不能替代真实研究质量验收。
